| A5

| c-morley (same); BsAtHome https://github.com/LinuxCNC/linuxcnc/discussions/4571#discussioncomment-18515435 ; grandixximo https://github.com/LinuxCNC/linuxcnc/discussions/4571#discussioncomment-18521152 ; rmu75 https://github.com/LinuxCNC/linuxcnc/pull/3580#issuecomment-3422052670
| The sidecar is the only reader of `linuxcnc.error_channel` and hands every error to ALL its clients (an `errors` entry with its own `seq`, a ring of the last N in the snapshot). **This holds only if no other process reads the channel.** AXIS or another GUI next to the sidecar shares the queue with it (a property of NML, `cms_in.cc`, CC-2) and each takes entries away from the other. Option `--no-error-channel`: the sidecar does not read the channel at all and leaves every error to the GUI; its clients then get no error text and command outcomes rest on RCS status and stat only.
| ✗ next to a GUI that reads the error channel, sidecar started without the option (`sl4_results.md` #10: 40 of 40 taken by the other reader, CC-2); ◐ with `--no-error-channel` (the GUI keeps its errors, the sidecar's clients lose the texts); ✅ only when the sidecar is the sole reader (`sl4_results.md` #2)

| A6
| Command outcome: finished / failed / aborted
| c-morley (same); grandixximo https://github.com/LinuxCNC/linuxcnc/discussions/4571#discussioncomment-18849954
| `command{id}` gives `command_result{id, outcome}` to exactly that client. The outcome is derived from the RCS status of the sidecar's own serial plus, for long commands (MDI, AUTO_RUN), from the transition of `exec_state` / `interp_state` to IDLE and from errors in the command's window -- a **heuristic** (CC-1, CC-3). Values: `completed`, `failed`, `aborted`, `accepted`, `unknown` (see `state-layer.adoc`).
| ◐ completed / failed / aborted / accepted to each client -- ✅ (`sl4_results.md` #1-9); error binding is a heuristic (CC-1, CC-3)

| A7
| Tool table and offsets edited outside the controller through the var file
| c-morley (same)
| Read: `tool_table`, `g5x_offset` (active coordinate system only), `g92_offset`, `tool_offset` are in the snapshot. The other coordinate systems (G54..G59.3) are not in stat. Writing through the sidecar is possible only as G10 through MDI (mode change, A3). CC-11.
| ◐ tool table / active coordinate system readable; editing ✗ (CC-11)

| A8
| End of program, for a part counter
| c-morley (same); grandixximo discussioncomment-18871710
| `program_end{reason: completed\|aborted\|error, seq}` in the state; derived from `interp_state` / `exec_state` transitions, channel errors and who sent the abort -- a **heuristic** (CC-4).
| ◐ completed / aborted / error ✅ (`sl4_results.md` #5-7); an abort from AXIS is not distinguished (CC-4)

| A9
| halui inside task limits the alternatives (panelui)
| c-morley (same); rene-dev https://github.com/LinuxCNC/linuxcnc/pull/4644
| The sidecar is an external client of a public protocol; a replacement panel can be one more websocket client. The sidecar exposes no HAL pins (out of scope).
| ◐ a replacement panel = a websocket client; no HAL pins

== Client side

How each LinuxCNC client would connect to the state layer and what stops it. "Facade" is
`clients/python/lcnc_state_client.py` `RemoteStat` / `RemoteCommand` / `RemoteErrorChannel`:
the same calls as `linuxcnc.stat/command/error_channel`.

| Client | Where it polls today (clone @ `2655e62fe6aa`) | How it would connect | What stops it

| `axis.py:3670` `s = linuxcnc.stat()`, `:4002-4003` `command()`, `error_channel()`, `:746` a second `stat()` in `LivePlotter`
| 3 lines: replace the constructors by the facade (`RemoteStat(url)` ...) + import; `s.poll()` once per `CYCLE_TIME` stays as is

Common to all: state arrives as a full snapshot plus patches, so a GUI does not need to change
its polling logic; it receives the same set of fields under the same names
(`linuxcnc.stat`). Errors come from the shared ring: the facade `RemoteErrorChannel` hands every
instance every entry (no "first poller") -- as long as no other process reads the NML error
channel (A5).
