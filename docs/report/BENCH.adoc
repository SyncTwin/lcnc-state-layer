== Pitfalls (measured where possible)

. **RFC 7396 replaces an array as a whole.** In `linuxcnc.stat` `joint` is 16 dictionaries
  (`EMCMOT_MAX_JOINTS`, although there are 3 joints), `joint_position` / `joint_actual_position`
  have 16 entries each, positions 9; during motion `joint` changes in 96.5 % of ticks
  (`logs/sl3_trace_summary.md`). So Merge Patch is 6.3 KB (40 % of full JSON), while the same
  Merge Patch on the "arrays as index dictionaries" model is 0.74 KB (arrays of objects) / 0.51 KB
  (all arrays); flatbuffers delta with whole arrays is 2.0 KB; Machinetalk's index deltas 0.16 KB.
  The price of the "by index" model in C++ is +50...170 us for DOM build/diff; on the client the
  parse is cheaper (28 against 182 us).
. **There are no empty ticks**: `heartbeat` and `taskbeat` change on every poll (100 % of ticks).
  Without them 3.3 % of ticks are empty on axis.ngc and 9.3 % on the gmoccapy program: while a
  program runs something is almost always moving; empty ticks are in the pauses. Bytes barely
  change (6 302 to 6 477 B: the "counter only" messages disappear).
. **Float noise**: in sim, positions at rest do not change in any tick
  (`logs/sl3_trace_summary.md`: "position fields changed anyway: none"); a 1e-4 deadband removes
  no bytes on this trace (6 477 to 6 477) and makes the Python diff 7.5 times dearer (recursive
  comparison `merge_patch.same()`). On real encoders, see the live run below.
. **Warm-up**: the first message (the warm-up pass) is dearer than the steady state: C++ JSON
  full encode 314 against 219 us, flatbuffers full 16.5 against 6.7; node cbor-x full 2 652
  against 116, @msgpack/msgpack 3 173 against 155 -- JIT / codec initialisation. For the patch
  variants the "first message" is a small first patch and its time is not representative
  (`cold_*` in the CSV).
. **The same JSON has different sizes** on different sides: Python and C++ print `1.0`, JS prints
  `1` (14 485 against 15 959 B). CBOR: nlohmann writes a float short when lossless (13 849 B),
  cbor2 always float64 (16 816 B); MessagePack likewise.
. **C++ Merge Patch parsing ends in a DOM**, not in a struct; the full variants end in a struct
  (`from_json`). Converting DOM to struct for every patch would cost another ~180 us (like
  `from_json` in "JSON full").
. **C++ JSON encoding is dear because of DOM building** (`to_json`): "JSON full" 219 us with
  DOM serialisation about equal to "CBOR full" 197 -- the cost is in the DOM, not in the format.
. **Python flatbuffers is pure Python** (package `python3-flatbuffers` 2.0.8): 2.3 ms per
  message, 8-27 times dearer than JSON/MsgPack with C acceleration. On the C++ side flatbuffers
  is 30-100 times cheaper than nlohmann.
. **NML today**: the status buffer is 20 480 B (`configs/common/linuxcnc.nml:11`), copied by
  every client on every poll (`emcmodule.cc:1028`) -- for reference; NML CPU was not measured.

== Conclusion for the JSON vs flatbuffers argument (by the numbers)

* **CPU does not decide at the GUI period.** At 0.1 s the dearest C++ variant (JSON MP, 461 + 182
  us) is 0.64 % of a tick; flatbuffers 0.01 %. About 100 times in relative terms, but in absolute
  terms ~0.6 ms per tick per client. The difference would matter with tens of clients on a weak
  ARM or with polling faster than 0.02 s -- not measured (ASSUMPTION, not a measurement: CPU
  grows linearly with the number of clients for parsing only; encoding in the sidecar is done once
  per encoding for all clients, `server.py _broadcast`).
* **Bytes are decided by the data model and compression, not by the format.** Full JSON 16 KB,
  Merge Patch 6.3 KB, Merge Patch with arrays by index 0.74 KB; flatbuffers full 6.4 KB, delta
  2.0 KB; CBOR/MsgPack save 13-15 % over JSON. permessage-deflate, which websocket gives for free,
  compresses **even full JSON to 313 B**, Merge Patch to 199 B at ~120 us of Python CPU.
* **Where flatbuffers is objectively better**: C++ CPU (encode 6.7 against 219-461 us, parse 3.6
  against 182-400), zero-copy reading of some fields (2.5 us). **Where JSON is better**: browser
  and Python without code generation (node JSON parse + patch apply 30 us; Python flatbuffers
  2.3 ms), readability, one JSON Schema; the drawback is that the schema has to be kept
  separately (here `schema/*.json`, from which the `.fbs` is generated, so the "second schema"
  need not be written by hand).
* **Proposal by the numbers**: the wire format is secondary; what matters first is (1) the array
  model (by index or index deltas), (2) permessage-deflate, (3) separating liveness counters
  from state. JSON + Merge Patch with arrays by index + deflate gives ~0.2 KB per update at < 1 %
  of a tick in C++.

== Live servos on a test bench, 2026-10-12

A manual run of the sidecar next to LinuxCNC on real EtherCAT drives. Raw data, the
recorder and the analysis are in `bench/live/servo_2026-10-12/` (`rec.py` -- recording client,
`ana.py` -- analysis, `ana_output.txt` -- its output, `trace_live_100ms.jsonl.gz` -- the sidecar's
trace, 701 ticks, `sidecar.log`).

**Bench.** A VM (2 vCPU, Debian 13, python 3.13). LinuxCNC `2.10.0~pre2` (a downstream Debian
package of 2.10 with a number of patches, see the note at the top) and linuxcnc-ethercat
`1.46.0` (downstream package with patches). On the bus 6 slaves in OP: 3x Inovance IS620N (X/Y/Z, CSP, cia402), Wecon
VD3E, SV660, coupler NX-ECC202. Configuration: a 5-axis mill `5axiskins` (X/Y/Z on live drives,
B/C a model), `[DISPLAY]CYCLE_TIME = 0.100`, so the sidecar period is 0.1 s. `websockets` 13.1
was put into a local `vendor/` directory (not part of this repository) from a wheel because the
machine had no apt access -- a deviation from the dependency policy "Debian packages only"; see
the README for the Debian package versions. The sidecar ran with `--allow-commands --trace`,
deflate on, deadband 0. One client (the recorder), on 127.0.0.1.

**Scenario.** 30 s of rest without torque. Then through the sidecar: `state ESTOP_RESET`,
`state ON`, `mode MANUAL`, `jog(JOG_INCREMENT, joint, 0, 5 mm/s, +2 mm)`, `jog(..., -2 mm)`,
`state OFF`, `state ESTOP`. A safety net in `finally`: OFF and ESTOP directly through
`linuxcnc.command`. Then 10x `set_block_delete` without torque. Torque was held
08:38:46-08:38:51 UTC. After switch-off the statusword of X/Y/Z = 592 (0x0250, switch on
disabled), `amp-enable-out` FALSE. LinuxCNC was started by hand, with no other NML client: only the
sidecar read `error_channel`, there was no competition for the error queue (CC-2).

**Pitfalls of the live run**

. **`state OFF` always "failed".** After `STATE_OFF` LinuxCNC shows `task_state ==
  STATE_ESTOP_RESET` (2), not `STATE_OFF` (3): in the trace the 2 appears in the first tick after
  the command. The effect rule (`EFFECTS["state"]`, `sidecar/lcnc_state/core.py`) waited for
  literally 3. Not a live-only problem: in sim `state OFF` was simply never sent.
. **Sending an NML command blocks the event loop.** `linuxcnc.command.*()` waits for the serial
  echo (20-91 ms) inside asyncio and ticks do not run meanwhile: outliers of 124.5 ms
  (ESTOP_RESET/ON) and 188.1 ms (OFF + ESTOP), then a catch-up tick after 12 ms. The ticker no
  longer "squeezes" missed ticks (`overran: skip`), so `seq` does not break, but the client sees a
  dip of 1-2 periods.
. **Encoder noise.** On a live drive the position changes every tick even at rest. Without
  `--deadband` the stream is never empty and Merge Patch always carries the joint arrays whole.
  This is an argument for arrays by index and for the deadband from the main table. The deadband
  was not measured on this noise.

**Fixed after the run** (checked in sim, LinuxCNC `2.10.0~pre2` from the same downstream package in a
container, `[DISPLAY]CYCLE_TIME = 0.100`).

. `state OFF`. Task itself never shows `STATE_OFF`: `determineState()` (`emctask.cc`) gives ESTOP
  on io estop, otherwise ESTOP_RESET while traj is off, otherwise ON. The effect of OFF is now
  `task_state != STATE_ON` (OFF from ESTOP stays ESTOP). Before: OFF from ESTOP / ESTOP_RESET / ON
  was `failed` after 1.06 s. After: `completed` in 84 / 84 / 105 ms.
. Send blocking. A thread does not help: `emcSendCommand` (`emcmodule.cc`) waits for the serial
  echo without releasing the GIL (measured: a thread doing `sleep(1 ms)` is silent for 20.4 ms
  on every command). Commands are now sent by a child process `sidecar/lcnc_state/sender.py`,
  the only owner of `linuxcnc.command`, one at a time, JSON lines. Scenario: OFF/ON/ESTOP
  transitions and 10 `set_block_delete` in a row. Before: tick period max 147.5 ms, at the
  client 154.7 ms. After: max 101.7 ms (min 97.9), at the client 105.0 ms; 0 `seq` gaps, replies
  in the order sent. `tests/sl4_live.sh`: 28 checks, 0 failures.

What this run did not cover: a G-code program on live axes (jog only), several clients, clients
over the network, homing, operation next to another process that reads `error_channel` itself
(CC-2).
